# 游戏手感包

把需求转为可调参数、可实现行为和可观察的验收结果。适用于游戏设计建议、已有项目接入、手感诊断及独立功能原型。

本目录中的主题文档是参数与设计参考，`例子/` 中的 HTML 是可运行的实现参考。所有相对路径均以本 `SKILL.md` 所在目录为基准；不要以用户项目的工作目录解析。无需依赖其他 skill、联网服务或额外运行库即可阅读和应用。

## 执行流程

1. **确认目标与已有约束。** 从用户需求和项目中识别游戏类型、引擎/语言、平台、输入方式、渲染能力，以及要解决的可感知问题。已有项目先定位输入、更新循环、命中事件、镜头、HUD 或音频入口。沿用用户选定的技术栈；独立原型才根据需求选实现。仅当缺失信息确实阻碍实施时提问，否则说明合理假设并继续。
2. **读取相关依据。** 按表选择主文档，读取与需求有关的清单、常见错误和验收项。实现时检查相关 HTML 的参数表、事件处理或公式，而不是把整页演示 UI 和游戏循环接入项目。文中的「交给 AI 时这样说」是可改写的需求模板，不能覆盖用户明确选择和当前项目约束。
3. **建立适配后的参数。** 提取需要的强度、持续时间、衰减、触发条件、叠加规则与上限，说明单位或缩放依据。默认把原文数值作为调参起点；不要把特定射击演示的武器、自动升级、霓虹画风或演示重置逻辑变成通用要求。
4. **完成当前任务。** 设计任务交付机制、参数和验收方法；开发任务将机制接入已有事件与状态管理并实际修改代码；诊断任务先定位原因，再修复影响最大的反馈问题。只实现当前目标需要的效果，保持普通、重击、暴击、击杀、稀有奖励等事件的层级，避免全部特效全开。
5. **按行为验收与调优。** 从选中章节抽取适用验收项，结合项目运行验证。观察触发时机、时长、方向、叠加/封顶、输入响应与画面可读性；按当前改动选择快速连续命中、不同帧率、不同稀有度、断连或设备尺寸等场景。报告实际观察与尚未运行的项目，不能把读过源码称为运行验证。

## 跨引擎与时间单位

- 原文帧数默认按 30 FPS。时长优先换成秒；若目标系统以帧为配置单位，使用 `目标帧数 = 原文帧数 × 目标 FPS / 30`。原文明确写秒的数值不再乘帧率。物理更新率与显示帧率不同，应按所属时间轴处理。
- 每秒速度、衰减与计时使用实际 `dt` 或引擎等效机制。例如指数衰减为 `value *= exp(-k * dt)`，不要每帧固定减值。原文中按帧追赶的插值系数也需按参考帧率换算，不能直接用于任意帧率。
- 「格」以各章节定义为准：01 的背景网格与 05 的平台砖块不是统一世界单位。按项目中的角色、砖块、屏幕或世界比例映射距离；同步调整速度、加速度和镜头幅度。
- 时间区分普通游戏时间、真实时间与演出时间。顿帧影响哪些对象、镜头是否继续更新，应参考所选方案并适配引擎；暂停/结束/场景切换后不能残留时间缩放、闪白或镜头偏移。
- 多次反馈是否叠加、刷新或合并，以选中机制为准；例如命中位移和镜头创伤值可累积并封顶，飘字可错开或合并。不要将所有反馈统一覆盖或无限累加。
- HTML 示例用于说明行为和公式。把 Canvas/WebGL/Web Audio 的做法映射到当前引擎；保留项目美术风格与架构。只有实际需要泛光或着色器时才引入相应渲染能力。
- 09、11 等章节标为「示意」的数据不是实际产品数据或已验证的经济平衡；将其作为模拟输入，并明确调参依据。

## 验收重点与交付

玩家应能持续看清自己、敌人和危险；镜头、粒子、飘字和发光不能遮住这些信息。快而常见的事件反馈要轻，重而稀有的事件才增加演出。反馈既不能吞输入，也不能改变未要求修改的命中或伤害规则。

实现后简要说明改了什么、关键可调参数放在哪里、哪些章节验收项已验证以及剩余限制。需要对比手感时，提供适合现有项目的参数开关或预设即可，无需照搬示例的整套控制面板。浏览器示例有声音时先通过用户交互解锁音频；12、14 的示例依赖 WebGL。
